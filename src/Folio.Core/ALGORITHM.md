# ClearNote core

`Folio.Core` 1.9.0 targets .NET 10 and uses only the standard library. Its internal assembly and namespace retain the Folio name for compatibility. Structured notes, review scheduling and file storage are separate from the desktop interface. Notes contain continuous text, inline styles and up to four imported pictures. Tags are derived from the text. The retained `PageSize` constants and `NoteBlock` model exist only for compatibility with older libraries. `LibraryStore.cs` owns ordinary persistence and archives; `LibraryStore.Profiles.cs` groups profile validation, conflict tracking and atomic profile saves; `LibraryStore.Drafts.cs` owns separate per-collection draft persistence; `LibraryStore.Deletion.cs` keeps deletion, shared-asset ownership and interrupted-deletion recovery together in a localized partial class.

## Continuous text and legacy compatibility

`CardDocument.Collection` is a validated Notes or Memo value. Omitted values in older libraries default to Notes. Existing IDs cannot move between collections through Upsert. Both collections share library snapshots, image assets and profile; Memo is excluded from scheduler selection and direct review recording. Schema 5 persists collection membership while accepting prior schemas 1 through 4. `CardDocument.Note` is a nullable `NoteContent`. A note contains required `Paragraphs` and optional `Images`, which defaults to an empty list for older libraries. Each `NoteParagraph` has a `Kind` of `body`, `heading`, `bullet`, `ordered` or `quote`, and a list of `Runs`. `HeadingLevel` defaults to 2 and accepts 1 through 6. `Number` defaults to 1 and accepts 1 through 1,000,000. A `NoteRun` contains `Text`, `Bold`, `Italic`, and optional `Foreground` and `Background`. Background applies to selected text as a highlight; it is not a paragraph, page or note background. Colors are six hexadecimal digits prefixed by `#`, normalized to uppercase by `NoteColors.Normalize` and structured copies. Null means automatic text color or no highlight. `NoteColors.IsValid` recognizes this same syntax; normalization throws for invalid values. These types reject unknown JSON fields. Paragraph kinds, number ranges, colors, required collections and text values are validated. Limits are 20,000 paragraphs, 100,000 runs and two million UTF-16 characters per note. The interface can scroll long notes rather than clipping them at a fixed canvas edge.

`NoteText.Read(card)` returns an independent structured copy, including independent picture references. `PlainText(card)` joins runs within each paragraph and separates paragraphs with a newline, without formatting markup. `HasContent(card)` and `HasContent(content)` accept non-whitespace text or at least one picture, so image-only drafts and posts are valid. `SetContent(card, content)` validates and copies its input into `card.Note`; it never changes creation or update timestamps, memory state or review history.

`MarkdownText.Parse(text)` accepts fast text shorthand. One through six leading hash marks followed by a space produce headings. A dash, asterisk or plus followed by a space produces a bullet. A positive number followed by a period or closing parenthesis and a space produces an ordered paragraph. Consecutive ordered paragraphs count upward from the first explicit start; another paragraph ends that sequence. A leading greater-than sign, followed by a space or the end of the line, produces a quote. Up to three leading spaces are allowed for these markers. Double asterisks produce bold; single asterisks or underscores produce italic, including nested bold and italic. Backslash-escaped punctuation stays literal; intraword underscores and unmatched emphasis markers also stay literal.

Fenced and indented code-looking text remains ordinary literal body text, including its markers. There is no code node, code-block rendering, HTML execution or link navigation. Balanced Markdown links, image syntax and HTML tags remain raw text; pictures are imported separately. CRLF and CR normalize to paragraph boundaries. Parsing uses iterative scans, precomputed bracket pairs and explicit stacks, with no regular expressions or recursive nesting. Extremely delimiter-dense lines fall back to literal text rather than allocating an unbounded number of inline tokens. The existing input, paragraph, run and character limits still apply.

When `Note` is null, `Read` adapts the legacy `Blocks` in ascending Y and then X order. Only text blocks contribute content. CRLF, CR and LF create paragraph boundaries; bold is retained, and font sizes of 26 or more become headings. Legacy image blocks are excluded from the text. Reading is side-effect free, and setting new text preserves the original blocks so the old layout and assets remain recoverable. An existing `Note` always takes precedence over legacy text.

New legacy image blocks are rejected by `Upsert`; new pictures use `NoteContent.Images`. Loading a new library, saving text or restoring a text-only backup does not create an `assets` folder. Text conversion preserves original legacy image files. Deleting the owning card removes its otherwise unshared managed legacy images under the same ownership rules as new images; unrelated local files and explicit manual archives remain untouched.

## Imported pictures and tags

`NoteImage` stores `AssetName`, `PixelWidth` and `PixelHeight`, with no inline bytes or arbitrary file paths. `NoteImages` exposes limits of four images per note, 20 MiB per import, 16,000 pixels per dimension and 40 million pixels total. Missing or null image collections, missing image fields and invalid references are rejected. The image list defaults to empty when omitted by older structured notes.

`LibraryStore.ImportImage(bytes, width, height)` accepts PNG and conventional 8-bit baseline, extended or progressive JPEG. It checks size and dimension limits, PNG chunk bounds and CRCs, JPEG segment bounds and frame/scan headers, complete end markers and agreement between declared and encoded dimensions. This is structural validation rather than a full pixel decoder; the desktop decodes and normalizes imports before invoking Core. The method snapshots caller bytes, writes and flushes a temporary file, then atomically moves it into `assets/<lowercase-SHA256>.png` or `.jpg`. Equal bytes reuse the same immutable asset. If another store publishes the same asset during that move, the winner is accepted only after full path, structure, dimension and hash validation. A damaged existing asset is rejected and preserved. Assets are durable before drafts or notes reference them. `GetImagePath(image)` checks the generated filename, path boundaries, symbolic links/junctions, size, encoded dimensions and content hash before returning a local path. Draft saves, library saves, library reads, backup validation and restore validation perform the same referenced-asset checks.

Desktop normalization is separate from Core storage. The app checks source limits before materializing Bgra32 pixels, applies EXIF orientations 1 through 8 and creates a fresh 96-DPI PNG without source metadata. A compressed photograph can be within the source limit while its lossless PNG exceeds 20 MiB. In that case, PNG encoding stops at the limit and retries from the cleaned original pixels with a proportional scale reduced by 0.8 each time. It preserves aspect ratio and alpha and never alters the source file. Input limits of 20 MiB, 40 million pixels and 16,000 pixels per side still apply. PNG clipboard byte arrays and streams retain alpha; a caller-owned seekable stream's position is restored. All selected files are read and normalized before asset import begins. Standard formats use Windows image decoding; WebP, HEIC/HEIF, AVIF and other optional formats require a compatible installed Windows codec.

Edits retain imported and legacy assets, including pictures no longer referenced by the current edit. Explicit note deletion removes that note's otherwise unshared managed assets. Pictures still used by another note, the current profile, a current draft or its recoverable previous version remain available. Backup includes the assets still present at export, covering draft-only pictures and preserved assets. A missing or changed referenced picture invalidates that candidate library or draft; the existing previous-save recovery rules apply. A malformed backup or missing draft-only picture rejects restoration before the healthy library is moved.

`NoteTags.Read(card)` and `Read(content)` return the first 64 distinct tags, without the hash prefix, preserving first-seen spelling and order. A tag starts with `#` at the start of text or after a boundary, followed by Unicode letters/digits, underscores or hyphens. Intraword hashes and repeated hash heading markers are excluded; `# ` heading syntax is not a tag. Tags span inline formatting runs but never paragraph boundaries. Case-insensitive duplicates are merged. Tags exceeding 64 Unicode scalar values are omitted rather than truncated. Supplementary Unicode letters, including CJK extension characters, are supported. `Matches(card, tag)` accepts a whole tag with or without `#`, compares case-insensitively and treats a null or whitespace filter as no filter. Tags do not create additional stored fields or rewrite note text.

## Review model and application policy

ClearNote uses the **FSRS-6 memory equations with fixed public defaults**, followed by ClearNote's own learning intervals and card selection policy. It does not reproduce Anki's complete scheduler. Parameter training, Anki learning stages, an Easy rating, calendar day cutoffs, load balancing, interval fuzzing and Anki synchronization are outside this implementation. A target retention of 90 percent is a model setting, not a guarantee of an individual's actual recall.

Official English sources, verified on October 19, 2026:

- [FSRS algorithm reference](https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm): the FSRS-6 default parameters, power law forgetting curve and short term stability update. The former `fsrs4anki` wiki now points to this reference.
- [TS-FSRS algorithm API reference](https://open-spaced-repetition.github.io/ts-fsrs/classes/FSRSAlgorithm.html): difficulty updates, recall and lapse stability equations, and the lapse stability cap.

The model represents stability `S` in days, difficulty `D` on a scale from 1 to 10, estimated retrievability `R`, and elapsed time `t` in actual days since the last rated review. Its 21 fixed parameters are:

```
[0.212, 1.2931, 2.3065, 8.2956, 6.4133, 0.8334, 3.0194,
 0.001, 1.8722, 0.1666, 0.796, 1.4835, 0.0614, 0.2629,
 1.6483, 0.6014, 1.8729, 0.5425, 0.0912, 0.0658, 0.1542]
```

The forgetting curve uses `factor = 0.9^(-1 / W[20]) - 1` and `R = (1 + factor * t / S)^(-W[20])`. Therefore, `R = 0.9` when `t = S`. Solving for an interval gives `I = S / factor * (targetRetention^(-1 / W[20]) - 1)`. The current target is fixed at 0.9, making the resulting interval equal to the updated stability.

The three ratings are `Again = 1`, `Hard = 2` and `Good = 3`. The first review initializes `S = W[G-1]` and `D = W[4] - exp(W[5] * (G-1)) + 1`. Subsequent difficulty updates apply linear damping and mean reversion toward `D0(4)`. Reviews at least one day apart use the long term recall or lapse stability formula. Reviews less than 24 hours apart use the FSRS-6 short term formula, with a minimum growth factor of 1 for Hard and Good. In ClearNote, the short term branch uses elapsed time rather than a time zone dependent calendar cutoff. Review logs preserve full timestamps.

ClearNote's application policy is:

1. A new card is immediately available to browse. Before its first rated review, the displayed recall estimate is zero to indicate that no memory state has been established.
2. Again schedules a learning review in **10 minutes**. Hard and Good use the model interval with a minimum of one hour. Stability is bounded from 0.001 to 36,500 days, and the maximum interval is 36,500 days. The first Good rating initializes stability to 2.3065 days; the first Hard rating initializes it to 1.2931 days.
3. `RecordBrowse(card, now)` calls the existing Good update once and marks only its newly appended review log `Automatic = true`. The desktop interface decides when a card has been sufficiently visible and suppresses repeated counting within a review session. Merely constructing or rendering a card is not a review. Earlier explicit reviews remain supported in saved data, and omitted `Automatic` fields default to false. This product policy does not change the FSRS equations.
4. Selection first considers all due cards. While any due card is available, future cards are excluded. Selection weight is `1 + 4 * (1-R) + min(10, overdueDays / max(1,S))`. If no card is due, the same weighted selection operates on the remaining cards. The caller's exclusion set is always respected; an exhausted set returns null. The interface controls session boundaries.
5. A rating timestamp earlier than the previous review is rejected so that a clock correction cannot reverse review history.

These selection weights, interval limits and automatic browse interaction are ClearNote product decisions, separate from the FSRS memory equations. `Apply` remains available for compatibility and testing; the current interface exposes no rating buttons.

## Library storage

Call `Load()` successfully before saving, deleting or creating backups. `Cards` returns independent deep copies, including nested text paragraphs and runs. Persist edits with `Upsert`. Empty notes are valid; the interface decides whether to retain an empty draft.

`IsNewLibrary` is read-only and true only after a successful load when neither `library.json`, `library.previous.json` nor an interrupted-deletion journal exists. `InitializeNewLibrary(cards)` validates and deep-copies the entire supplied collection, then saves it in one commit with its first recovery copy. It returns false without changing an existing saved collection. The desktop uses this boundary for two ordinary welcome notes. Saving an empty collection, deleting every note, restoring an empty archive or recovering a previous library never re-enables welcome initialization. Unsent drafts remain independent and do not prevent first-run initialization.

- `library.json` saves `version: 5` and `cards`, while readers accept versions 1 through 5. The optional `note` field keeps original version 1 libraries compatible. New text style, automatic-review and image-list fields have compatible defaults. Required card identities, legacy block fields, memory states and review records remain protected against missing JSON fields. Paragraph fields remain required whenever a note is present.
- `library.previous.json` holds the preceding complete ordinary save. Saving first writes a temporary file and flushes it to disk, then atomically replaces the main file with `File.Replace`. The initial save also creates a recovery copy. Explicit deletion instead replaces both versions with the same remaining collection, so recovery cannot resurrect deleted content.
- Loading a damaged main file, including a missing referenced image, tries the previous save. Successful recovery repairs the main file atomically and exposes a message through `RecoveryNotice`.
- If both files are invalid, `Load()` throws `InvalidDataException` and disables writes. The files remain available for recovery. A successful `Restore` can unlock this state.
- Before a write or backup, a SHA256 comparison detects changes outside this store and requires a reload rather than overwriting them. A per-instance lock serializes operations. The desktop application also enforces one running instance per library.
- Legacy images remain in their existing `assets` directory. Referenced legacy files are validated as PNG, JPEG, GIF, BMP or TIFF and are limited to 64 MB each. They are retained for recovery rather than rendered in new continuous notes. New imported pictures use the stricter validation and 20 MiB limit described above.
- Text conversion does not delete existing files. Explicit card deletion removes only the deleted card's owned managed images which have no retained owner; it never changes an uploaded source file outside the library or an existing manual archive.

## Deleting local content

`Delete(id)` validates the remaining collection and computes the removed card's owned picture names, including preserved legacy image blocks. A picture remains when another active note, the local profile, either collection's current or previous draft references it. All four draft files are inspected because either version in either collection can be recovered independently. If profile or draft ownership cannot be validated, destructive picture cleanup fails while preserving the card and files. Unrelated draft corruption does not prevent deleting a text-only card. The desktop saves a dirty composer before deletion so its current picture ownership is visible to storage.

Before changing saved content, deletion rejects linked paths, folders occupying data or image paths, read-only files and exclusive file locks. It then flushes a small `delete.pending.json` intent containing only the card ID and disposable asset names, with no copy of deleted note text. It atomically replaces the recovery library and main library with the same remaining collection, deletes the unshared images, and removes the intent last. It creates no pre-delete archive or hidden full-data copy. The interface also creates no automatic daily archive; explicit manual backup and restore remain available.

If an unexpected interruption occurs after the intent is saved, the intent remains as an idempotent retry record. On the next load, its card ID is filtered from either candidate library before asset validation, so an old recovery snapshot cannot resurrect the deleted note or fail merely because its deleted picture is already gone. Loading finishes both filtered snapshots and the remaining asset cleanup before clearing the intent. Ownership is checked again before deleting a picture. An access failure is surfaced as an unfinished-deletion error rather than reported as success; resolving it and reloading completes cleanup. An invalid intent is preserved and rejected. Explicit manual archives remain independent historical snapshots and are never rewritten by note deletion.

## Unsent composer drafts

`ComposerDraft` contains a stable `CardId` and a structured `Content`. `LoadDraft`, `SaveDraft` and `ClearDraft` accept a NoteCollection overload. Their original no-argument collection APIs retain Notes behavior with fixed `draft.json` and `draft.previous.json` filenames; Memo uses `memo-draft.json` and `memo-draft.previous.json`. Identity values are never used as paths. Each collection keeps independent recovery flags and conflict hashes. Drafts do not enter `Cards` until Post upserts a card using the same identity. Retrying that upsert updates the same card. A draft whose identity is already present in `Cards` is suppressed on read, protecting against a crash after posting but before clearing. When that draft is valid, reading also finishes the interrupted clear so a later card deletion cannot resurrect it; failed cleanup produces a recovery notice and preserves the files. Invalid originals are never overwritten. Stale autosaves with a submitted identity are rejected.

Draft writes deep-copy and validate text and picture references, check that all imported image files exist and remain valid, flush a temporary file to disk and atomically replace the primary with a previous-save recovery copy. SHA256 checks on both files reject changes made outside the store until an explicit draft reload. A successful clear atomically writes a JSON null tombstone and also replaces the older recovery copy with null, so a completed clear cannot recover already-sent content. The first successful draft save creates a recovery copy. A failed validation or write leaves the original complete files available; temporary files belonging to that operation are cleaned up.

Backup reads a separate draft snapshot and never reloads the composer's saved hashes or clears its draft files. If a composer has already inspected its draft and either file changed externally, backup fails until an explicit draft reload; a subsequent stale autosave remains rejected. The snapshot's own hashes are checked again before ZIP publication, including when no draft was readable, so backup cannot silently adopt changes during export.

Regular `Load` and note editing do not depend on draft readability, except when an interrupted picture deletion must establish ownership before destructive cleanup. `LoadDraft` returns an independent valid draft, a valid previous draft when available, or null. It exposes any recovery issue through `DraftRecoveryNotice`. A missing primary and valid previous save produce a nonblocking notice. An unreadable or invalid draft produces `DraftSaveBlocked = true`: autosave and clear are rejected, and damaged originals are not overwritten or repaired in place. The saved card collection remains usable. The notice and explicit blocking flag have different purposes and the interface must check the flag before disabling draft saving.

## Local author profile

`UserProfile` contains `DisplayName` (default `You`) and an optional `Avatar` reference. It is one current identity for the library, not an author snapshot stored in each note. `LoadProfile()` returns an independent copy; a missing `profile.json` returns the default without creating a file. Existing notes and libraries need no migration.

`SaveProfile(profile)` trims and NFC-normalizes the display name, accepts 1 through 80 Unicode text elements, and rejects invalid Unicode, control characters and line separators. Avatar references are independently copied and validated with the same asset name, path, dimensions, encoded structure and content hash checks as note pictures. The optional `profile.json` is limited to 64 KiB before hashing or reading. Saving flushes a unique temporary file and atomically replaces the profile; failed operations preserve the prior file and clean only their own temporary file. SHA256 checks reject external changes until an explicit profile reload. Changing or removing an avatar retains the immutable former asset for recovery and backups.

An unreadable or invalid profile returns the default identity with `ProfileRecoveryNotice` and `ProfileSaveBlocked = true`. Profile writes remain blocked to preserve the original file. Regular library and draft loading and saving remain available. A later explicit reload can adopt a recovered valid profile. Backup rejects an unreadable, invalid or externally changed profile rather than silently omitting it; a valid optional profile and its avatar are included, and the source profile hash is checked again before publishing the ZIP. Restore validates the profile and avatar before moving the current library. Older backups without a profile restore successfully with the default identity.

## Portable usage data

`PortableStorage.Prepare(softwareDirectory)` returns `LibraryPath = softwareDirectory/Log/Data` and `BackupPath = softwareDirectory/Log/Backups`, plus an optional migration notice. No application-data directory is used. Library files, retained assets, composer drafts, `Data/profile.json`, backup files, migration staging and restore rollback folders remain beneath the software's `Log` folder. Separating Data from Backups lets restore preserve older Data beside it under Log without moving the backup collection.

On first preparation, old software-level `Data` and `Backups` trees are copied into these locations. An old `Data/Backups` subtree is routed to `Log/Backups`. File hashes are verified after copying; a staged library is validated before publication. Any necessary library recovery modifies only the staged copy. Referenced legacy images are checked by the normal library validator. Backup ZIPs are copied byte for byte; their archive contents undergo full validation when restored. Source folders and files are preserved. Links and junctions are rejected. Different existing destination bytes cause a clear conflict instead of silently merging libraries; matching partial copies can resume safely. A complete new Data folder is published with one directory move when the destination is absent. The final marker `Log/portable-storage.json` prevents preserved stale source folders from overriding later active notes. Temporary cleanup is restricted to the migration's own directory beneath Log.

## Backup and restore

`Backup(zipPath)` first completes any durable pending deletion before planning or serializing an archive. If its cleanup remains blocked, backup fails and preserves any existing destination ZIP. Thus a newly exported archive cannot resurrect content already covered by a deletion intent. It then exports the current library, a valid unsent draft when available, an optional valid local profile, and all existing imported and legacy asset files with `backup-manifest.json`. The manifest records each file's size and SHA256 hash, including optional `draft.json`, `memo-draft.json` and `profile.json`. A recovered valid draft can be exported without changing its damaged source files. An invalid draft with no valid recovery is omitted when its unchanged source bytes can be inspected, and remains preserved in the original library with its recovery notice. Inaccessible or concurrently changed draft files abort backup publication rather than presenting an incomplete snapshot as successful. Invalid profiles abort backup and remain preserved. Store the ZIP outside the library directory; the desktop default is the sibling `Log/Backups` folder. `Restore` accepts complete backups in this format, including original version 1 libraries and manifests and older backups without drafts or profiles. The manifest format remains version 1; new library JSON uses version 5. Invalid optional draft or profile content rejects restoration before the current library changes.

Backup and restore use the same expanded-size policy: at most 100,002 entries, 64 MB per file, 8 MB for the manifest and 2 GB in total, including the library and manifest. Before creating a temporary ZIP, backup measures the serialized manifest with fixed-width hash placeholders and checks all planned file lengths. The final manifest is checked again before publication. Asset copies stream their bytes, verify the planned length and compute their hashes during writing. An input file that changes size aborts the backup, and an existing destination backup is replaced only after the complete archive is closed successfully. A rejected plan leaves the library and any previous destination backup intact.

`Restore(zipPath)` **replaces the entire library**. It first extracts into a dedicated sibling staging directory and validates names, duplicates, path boundaries, symbolic link flags, expanded sizes, all manifest hashes, document structure, an optional local profile and referenced images. Unexpected paths or missing entries cause rejection before the existing library is changed. Limits are 2 GB of extracted data, 64 MB per file and 100,002 archive entries. The library JSON also has a 64 MB limit; a profile has the stricter 64 KiB limit.

After validation, the original directory is preserved beside the library as `LibraryName.before-restore-timestamp-id`. `RecoveryNotice` reports that path. If the staged directory cannot be installed, the original directory is moved back. Cleanup applies only to the staging folder created by the current operation after checking its resolved absolute path. It never deletes the preserved library or an earlier output. New text notes do not decode legacy images or hold their files open.
